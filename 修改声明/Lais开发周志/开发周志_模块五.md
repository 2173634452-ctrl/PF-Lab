## 一、完成的工作

模块五是整个系统的"门面"——之前四个模块各自实现了独立的功能，但用户打开程序后怎么用、谁能用哪些功能、报告怎么查看，这些问题还没有统一解决。本周的工作就是把这些问题一一落实。

### 1. 权限系统完善（5.1）

登录功能之前就已经有了，admin/guest 两个账户、三次尝试机会这些逻辑没动。但权限检查函数 `has_permission()` 有一个漏洞：访客登录后按 0（退出）或 9（清屏）会被拒绝。这两个操作跟数据安全没关系，纯粹是系统交互，不应该受角色限制。

修改就加了3行代码——在管理员全权限判断之后、访客白名单判断之前，插入了一个系统级操作的放行分支。加上之后访客的权限矩阵就完整了：能看数据概览（5）、能看分析报告（7）、能清屏（9）、能退出（0），其他涉及数据修改或敏感分析的功能一律不开放。

### 2. 角色感知菜单（5.2）

原来的主菜单不管谁登录，显示的都是同一套选项。`show_main_menu()` 函数甚至不需要任何参数。

这次的改动思路是让菜单"知道自己展示给谁看"。给函数加了 `UserRole role` 参数，内部用 `if (role == ROLE_ADMIN)` 来决定哪些选项出现。管理员看到全部9个功能，访客只看到5、7、9、0四项。菜单顶部加了一行身份标签——"当前用户: 管理员 (admin)"或"当前用户: 访客 (guest)"——这样使用者随时清楚自己当前以什么身份在操作。

这里同时做了一层安全防护。菜单不显示某个选项只是"体验层面"的过滤，如果用户在命令行里直接输入了被隐藏的功能编号（比如访客输了1），`handle_menu_choice()` 入口处的 `has_permission()` 检查会直接拦截。等于菜单过滤是第一道防线（让访客不知道有这些功能），权限检查是第二道防线（即使知道也用不了）。这种双层控制在带权限的系统中是标准做法。

### 3. 报告查看功能（5.2/5.3）

模块三的分析结果写到了 `reports/` 目录下的 CSV 文件里，之前没有一个便捷的方式在主界面直接查看这些报告。这次新增了 `display_text_file()` 函数，用 `fgets` 逐行读取文件并格式化输出到控制台。

做了几个细节处理：文件不存在时不崩溃，只提示"请先执行相应的分析功能"；最多显示200行，防止长文件刷屏；自动去除行尾的 `\r` 和 `\n`，兼容 Windows 和 Linux 换行差异。case 6 显示预警报告，case 7 同时显示统计分析报告和数据概览文件，两个入口都走同一个函数，逻辑没重复。

### 4. 全模块调度整合（5.3）

`handle_menu_choice()` 现在是整个系统的中央调度器。case 1/2/3 分别进入模块一二三的子菜单循环，case 4 是模块四的预览占位卡片（后面实现模块四时直接替换就行），case 5 展示内存中的数据概览，case 6/7 查看报告文件，case 8 是备份恢复快捷入口，case 9 清屏。所有模块的入口统一在一个地方管理，新增模块只需要在 switch 里加一个 case。

`UserRole` 的传递链是从 `main()` 开始，经过 `login_user()` 拿到角色，然后传给 `show_main_menu()` 和 `handle_menu_choice()`。选择用参数传递而不是全局变量，主要考虑是显式依赖更好追踪——看函数签名就知道它需要角色信息，不用翻全局变量定义。

## 二、碰到的问题

### 问题一：退出确认时弹了两遍提示

在 `main.c` 的处理循环里，用户输入0退出时，代码先执行了 `printf("确认退出系统？(y/n): ")`，紧接着又调了 `confirm_action("退出系统")`。而 `confirm_action` 内部做的事情就是 `printf("%s (y/n): ", prompt)`——换句话说，用户会被提示两次：

```
确认退出系统？(y/n): 退出系统 (y/n):
```

两个提示摞在一起，信息重复而且看着有点奇怪。如果只留 `confirm_action` 那一步，它输出的内容是"退出系统 (y/n): "，本身已经足够清晰，前面那句 `printf` 纯属多余。删掉之后退出流程就干净了。

### 问题二：输入错误时的清屏时机不对

主循环里 `scanf` 读不到合法整数时的处理顺序原本是：

```
clear_console();   // 先清屏
printf("输入错误…");  // 再打错误信息
清空缓冲区;
continue;          // 回循环开头重绘菜单
```

问题是清屏之后才打错误信息，紧接着循环回到 `show_main_menu` 又画了一整屏菜单，那条错误提示一眨眼就没了——不是没显示，但用户基本来不及看。调整后的顺序是先显示错误信息、清空缓冲区，最后再清屏，这样错误提示停留在屏幕上的时间足够用户读完，然后才清掉重绘菜单。

这两个问题都不涉及核心逻辑，纯粹是交互细节上的疏漏。之所以没在提交前发现，主要还是当时注意力都放在权限系统和菜单调度上了，没仔细过一遍主循环里的每行代码。好在后面专门做模块五审查时逐行读了一遍，这些小问题就都暴露出来了。修复本身改不到十行代码，但体验上差别还是挺明显的。

## 三、收获

1. **权限模型选型要匹配场景**。这个系统只有两个角色、九种功能，用 RBAC 枚举加一个判断函数就够了，不到20行代码。如果做一个完整的 ACL 表或者引入外部权限配置文件，反而把简单问题复杂化了。选型的时候不被"最佳实践"牵着走，而是看当前场景到底需要什么，这点挺重要的。
2. **参数传递比全局变量省心**。把 `UserRole` 作为参数一路传下去，改动的函数签名虽然多了，但好处是随时能追踪角色信息的来源和流向。之前用全局变量的版本跑起来也没什么问题，但排查逻辑时老得确认"这个变量到底在哪儿被改过"——参数传进来至少不用操这个心。
3. **报告查看用文件 I/O 而不是内存传递是个好的解耦选择**。如果模块五要直接读模块三的内存数据结构，两个模块就耦合在一起了，任意一方改结构另一方都得跟着改。通过 CSV 文件做中间层，模块三只管写文件，模块五只管读文件，两边独立演进互不影响。代价是多了几次磁盘 I/O，但对于这种分析结果查看的场景完全够用。
4. **占位设计让未完成模块不阻塞集成**。模块四还没开发，但 case 4 放了一张功能预览卡片，告诉用户这个入口将来会有什么。这比留空或者输出一行"开发中"更好——预览卡片本身就是一种活的文档，后续实现模块四的同事看一眼就知道这个位置需要接什么。
