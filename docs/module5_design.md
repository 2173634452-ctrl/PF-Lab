## 5.1 权限模型设计 — 为什么选择 RBAC？

### 问题背景

本系统面向两类用户：**管理员**（养殖基地技术人员）和**访客**（外部参观/审计人员）。前者需要完整的操作权限，后者仅需查看分析结果。任务书明确要求"管理员可以使用全部功能，访客只允许使用部分功能"。

### 为什么用 RBAC 而非 ACL 或简单布尔标记？

| 维度       | RBAC（角色基）            | ACL（访问控制列表）   | 布尔标记 `is_admin` |
| ---------- | ------------------------- | --------------------- | ------------------- |
| 扩展性     | ✅ 新增角色零改动调用方   | ⚠️ 需逐资源添加条目 | ❌ 需改所有判断分支 |
| 可读性     | ✅ `has_permission()` 集中 | ⚠️ 分散在各处        | ❌ if-else 散落各处 |
| 粒度控制   | ✅ 按功能编号统一管理     | ✅ 按资源逐条定义     | ❌ 仅二元判断      |
| 实现复杂度 | 低（枚举 + 单函数）       | 中（需维护 ACL 表）   | 低（但维护成本高）  |

**选择 RBAC 的理由**：

1. **当前需求恰好是角色维度**：管理员 vs 访客，与 RBAC 天然匹配
2. **最小实现复杂度**：仅需一个 `UserRole` 枚举 + `has_permission()` 函数，约 20 行代码
3. **集中式权限判断**：所有权限逻辑集中在 `auth.c:has_permission()`，修改权限只需改一处
4. **预留扩展性**：若将来新增"审计员"等角色，只需在枚举中添加并在 `has_permission()` 中增加一个 `if` 分支

### 权限矩阵

| 功能编号 | 功能名称       | 管理员 | 访客 | 说明                           |
| :------: | -------------- | :----: | :--: | ------------------------------ |
|    1     | 数据基础操作   |   ✅   |  ❌  | 含加载/浏览/筛选/排序/修改/删除 |
|    2     | 数据预处理     |   ✅   |  ❌  | 异常值/缺失值/滤波              |
|    3     | 统计分析       |   ✅   |  ❌  | 基本统计量/预警/相关性          |
|    4     | 预测分析       |   ✅   |  ❌  | 线性回归模型（开发中）          |
|    5     | 查看数据概览   |   ✅   |  ✅  | 记录数/有效率/预处理统计        |
|    6     | 查看预警报告   |   ✅   |  ❌  | 缺氧预警/盐度突变               |
|    7     | 查看分析报告   |   ✅   |  ✅  | 统计报告 + 数据概览             |
|    8     | 数据备份与恢复 |   ✅   |  ❌  | 备份/恢复 CSV                   |
|    9     | 清屏           |   ✅   |  ✅  | 系统级操作                      |
|    0     | 退出系统       |   ✅   |  ✅  | 系统级操作                      |

**访客权限的设计逻辑**：功能 5 和 7 是"只读查看"类操作，不修改数据，对系统无副作用。功能 9 和 0 是系统级交互，与数据无关。其余功能涉及数据修改或敏感分析，仅对管理员开放。

### 权限检查函数

```c
bool has_permission(UserRole role, int feature) {
    if (role == ROLE_ADMIN) {
        return true;              // 管理员：全部开放
    }
    if (feature == 9 || feature == 0) {
        return true;              // 系统级操作：所有角色
    }
    if (role == ROLE_GUEST) {
        return (feature == 5 || feature == 7);  // 访客：仅只读查看
    }
    return false;
}
```

**设计要点**：
- 管理员判断在最前，短路后续所有检查——效率最优
- 系统操作（清屏/退出）独立判断，不随角色变化
- 访客权限使用白名单模式（显式列举而非排除），安全性更高——新增功能默认为"不可访问"

## 5.2 登录认证设计

### 账户体系

| 角色     | 用户名 | 密码     | 对应现实身份           |
| -------- | ------ | -------- | ---------------------- |
| 管理员   | admin  | 123456   | 养殖基地技术人员       |
| 访客     | guest  | guest    | 外部参观人员/审计人员  |

账户凭据以编译期常量形式硬编码于 `auth.c` 中：

```c
const char admin_user[] = "admin";
const char admin_pass[] = "123456";
const char guest_user[] = "guest";
const char guest_pass[] = "guest";
```

### 为什么硬编码凭据而非文件/数据库存储？

| 存储方式     | 优点             | 缺点                     | 适用场景         |
| ------------ | ---------------- | ------------------------ | ---------------- |
| 编译期常量   | 零依赖，无条件   | 修改需重新编译           | ✅ 教学/原型系统 |
| 配置文件     | 修改无需重编译   | 需解析逻辑 + 明文风险    | 小规模内部工具   |
| 数据库       | 安全，可管理     | 引入外部依赖             | 生产系统         |
| 加密存储     | 安全性高         | 实现复杂                 | 安全敏感系统     |

**结论**：本系统为课程实践项目，账户体系仅用于演示权限分级，采用编译期常量是最简单且符合场景的选择。真实生产系统应使用数据库 + 哈希存储。

### 登录尝试次数限制

```c
for (int attempt = 0; attempt < 3; ++attempt) {
    // 输入用户名密码 → 验证 → 成功则返回
}
return false;  // 3次均失败，拒绝登录
```

**为什么是 3 次？** 这是安全领域的常见实践（如 UNIX `login`、SSH 默认配置）。3 次尝试在"用户体验"与"防暴力破解"之间取得平衡——太少（如 1 次）对误输入不友好，太多（如无限次）存在暴力破解风险。每次失败后提示"用户名或密码错误"，不区分是用户名错还是密码错，避免攻击者通过错误信息推断有效用户名。

### 登录流程集成

`main()` 在程序入口处调用 `login_user()`，返回值决定是否进入主循环：

```c
if (!login_user(&role)) {
    printf("登录失败，程序退出。\n");
    return 1;
}
```

`UserRole` 通过指针传出，后续贯穿整个程序生命周期——从 `main()` → `show_main_menu()` / `handle_menu_choice()`，形成完整的角色传递链。

## 5.3 菜单交互设计

### Role 参数的传递方式 — 为什么用函数参数而非全局变量？

| 方式             | 优点                 | 缺点                         |
| ---------------- | -------------------- | ---------------------------- |
| 全局变量         | 无需改函数签名       | 隐式依赖、难测试、易被意外修改 |
| ✅ 函数参数传递  | 显式依赖、类型安全、纯函数可测试 | 需改动函数签名               |

**选择参数传递的理由**：

1. **显式优于隐式**：阅读 `show_main_menu(UserRole role)` 即知该函数依赖角色信息，无需查找全局变量定义
2. **不可变性保证**：参数传递确保菜单函数不会意外修改角色（若用全局变量 + 指针则可能被篡改）
3. **可测试性**：纯函数（只读参数 + 只输出）比依赖全局状态的函数更容易单元测试
4. **改动量可控**：仅需改动 2 个函数签名（`show_main_menu`、`handle_menu_choice`）和 1 个调用点（`main.c`）

### 双层权限控制

本系统采用**双层权限控制**架构：

```
用户输入功能编号
    │
    ▼
第一层：菜单可见性 (show_main_menu)
    ├── 根据 role 决定哪些选项显示
    └── 访客看不到选项 1/2/3/4/6/8
    │
    ▼
第二层：权限校验 (handle_menu_choice)
    ├── has_permission() 检查
    └── 即使直接输入隐藏编号也被拦截
```

**为什么需要两层？** 第一层（菜单过滤）提供良好的用户体验——访客不会看到自己无法使用的功能。第二层（权限校验）提供安全保障——即使用户通过直接输入编号绕过菜单显示，也会在入口处被拦截。这是典型的"前端展示 + 后端校验"防御模式。

### 菜单渲染实现

```c
void show_main_menu(UserRole role) {
    printf("  当前用户: %s\n", role == ROLE_ADMIN ? "管理员 (admin)" : "访客 (guest)");
    if (role == ROLE_ADMIN) {
        printf(" [1] 数据基础操作\n");
        printf(" [2] 数据预处理\n");
        // ...
    }
    printf(" [5] 查看数据概览\n");       // 所有角色可见
    printf(" [7] 查看分析报告\n");       // 所有角色可见
    printf(" [9] 清屏\n");               // 系统级
    printf(" [0] 退出系统\n");           // 系统级
}
```

使用 `if (role == ROLE_ADMIN)` 而非 `if (role != ROLE_GUEST)` 的原因：前者是白名单思维（admin 显式授权），后者是黑名单思维（非 guest 即允许）。若将来增加 `ROLE_UNKNOWN` 角色，白名单方式默认拒绝，更安全。

### 权限校验入口

```c
void handle_menu_choice(int choice, WaterDataset **dataset, UserRole role) {
    if (!has_permission(role, choice)) {
        printf("权限不足：当前用户角色无权访问此功能。\n");
        return;
    }
    switch (choice) { ... }
}
```

权限校验在 `switch` 之前执行，是**统一入口守卫**——所有 case 分支无需各自检查权限，避免遗漏。

## 5.4 报告查看设计

### 文件式报告显示

模块三（统计分析）将结果写入 `reports/` 目录下的 CSV/TXT 文件。模块五通过 `display_text_file()` 函数读取并展示这些文件：

```
case 6 (预警报告):
    display_text_file("reports/warning_report.csv", "预警报告");

case 7 (分析报告):
    display_text_file("reports/statistics_report.csv", "统计分析报告");
    display_text_file("reports/data_overview.txt", "数据概览报告");
```

### 为什么用文件读取而非内存传递？

| 方式           | 优点                 | 缺点                     |
| -------------- | -------------------- | ------------------------ |
| 内存传递       | 快速、无 I/O 开销    | 需定义报告数据结构、紧耦合 |
| ✅ 文件读取    | 解耦、持久化、可审查 | 需文件存在、I/O 延迟     |

**选择文件读取的理由**：

1. **解耦**：模块五与模块三/四之间通过文件"约定接口"通信，无需了解彼此的内部数据结构
2. **持久化**：报告文件可被外部工具（Excel、文本编辑器）直接打开，不依赖程序运行
3. **实现简单**：`fgets` 逐行读取 + 格式化输出，约 20 行代码
4. **容错**：文件不存在时友好提示而非崩溃

### 显示函数设计

```c
static void display_text_file(const char *filepath, const char *title) {
    FILE *fp = fopen(filepath, "r");
    if (!fp) {
        printf("[提示] %s 文件不存在 (%s)。\n", title, filepath);
        printf("请先执行相应的分析功能生成报告。\n");
        return;                 // 优雅降级，不中断程序
    }
    // 逐行读取并格式化输出，最多200行
    while (fgets(line, sizeof(line), fp) && line_count < 200) { ... }
    fclose(fp);
}
```

**设计要点**：
- **`static` 限定**：函数仅在本文件内使用，不暴露给外部——遵循最小可见性原则
- **行数上限 200**：防止大文件刷屏，超出时显示截断提示
- **行尾清理**：去除 `\n` 和 `\r` 以便统一格式化输出，兼容 Windows/Linux 换行差异
- **前向声明**：函数定义在调用点之后，需要在文件顶部声明。这是 C 语言的常见模式——将 `static` 辅助函数放在文件末尾，通过顶部前向声明告知编译器

## 5.5 模块入口统一设计

### 子菜单循环模式

所有模块的子菜单遵循统一的交互模式：

```
进入子菜单
    │
    ▼
while (sub_choice != 0):
    ├── 显示子菜单选项
    ├── 读取用户输入
    ├── 输入校验（scanf 返回值检查）
    ├── 清理输入缓冲区（while (getchar() != '\n')）
    ├── 调用子菜单处理函数
    └── 选择 0 → 退出循环，返回主菜单
```

这种模式在模块一至四中保持一致。模块五的 `handle_menu_choice` 作为**中央调度器**，负责将用户选择路由到对应模块的子菜单入口。

### 模块调度架构

```c
void handle_menu_choice(int choice, WaterDataset **dataset, UserRole role) {
    // 权限守卫
    if (!has_permission(role, choice)) { return; }

    switch (choice) {
        case 1: → 模块一子菜单循环 (data_io)
        case 2: → 模块二子菜单循环 (preprocess)
        case 3: → 模块三子菜单循环 (analysis)
        case 4: → 模块四入口 (model, 开发中)
        case 5: → display_overview()
        case 6: → 预警报告查看
        case 7: → 分析报告查看
        case 8: → 备份与恢复入口
        case 9: → clear_console()
        case 0: → 已在 main() 中处理, 不会到达此处
    }
}
```

**模块四占位设计**：当前模块四未完成，case 4 显示功能预览卡片而非空操作。这样做的好处：
- 用户能感知该功能的存在和预期内容
- 后续实现模块四时，只需替换 case 4 的内容，不影响其他任何 case 分支
- 预览卡片本身就是"活文档"——描述该模块将提供什么

## 附录A：模块五程序流程

```
程序启动 (main.c)
    │
    ├── 设置控制台 UTF-8 编码 (Windows)
    │
    ├── 登录认证 (auth.c)
    │     ├── 输入用户名/密码 (最多3次)
    │     ├── 匹配 admin/guest 账户
    │     ├── 成功 → 返回角色 → 继续
    │     └── 3次失败 → 输出提示 → 退出程序
    │
    ▼
主循环 (while true)
    │
    ├── show_main_menu(role)
    │     ├── 显示当前用户角色标签
    │     ├── role == ADMIN → 显示全部选项 [1]-[9],[0]
    │     └── role == GUEST → 仅显示 [5],[7],[9],[0]
    │
    ├── 读取用户选择 (scanf)
    │     ├── 输入错误 → 清缓冲 → continue
    │     └── 选择 0 → 确认退出 → break
    │
    └── handle_menu_choice(choice, dataset, role)
          │
          ├── has_permission(role, choice) — 权限守卫
          │     ├── 无权限 → 提示 → return
          │     └── 有权限 → 继续
          │
          ├── case 1: 模块一子菜单 (数据操作)
          ├── case 2: 模块二子菜单 (预处理)
          ├── case 3: 模块三子菜单 (统计分析)
          ├── case 4: 模块四预览卡片 (预测分析)
          ├── case 5: display_overview() (数据概览)
          ├── case 6: display_text_file() (预警报告)
          ├── case 7: display_text_file() ×2 (分析报告)
          ├── case 8: 备份/恢复快捷入口
          └── case 9: clear_console() (清屏)
```

## 附录C：与模块四的兼容设计

模块五在 case 4 处预留了预测分析模块的入口。当前为功能预览卡片，后续实现模块四时：

1. 在 `ui.h` 中声明 `show_model_submenu()` / `handle_model_submenu()`
2. 替换 `ui.c` case 4 的内容为子菜单循环（与 case 1/2/3 模式一致）

这种"接口先行、实现后补"的设计确保了模块间的低耦合性。
