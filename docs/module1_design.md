## 1.1 数据结构设计 — 为什么使用动态数组？

在 `common.h` 中，`WaterDataset` 使用**动态数组（动态内存分配）**存储水质记录，而非静态数组。原因如下：

### 动态数组 vs 静态数组

| 维度         | 动态数组（本系统采用）           | 静态数组                         |
| ------------ | -------------------------------- | -------------------------------- |
| 内存分配时机 | 运行时（`malloc`/`realloc`） | 编译时（栈上或静态区）           |
| 内存大小     | 按需调整，初始1000条，满则翻倍   | 固定大小，编译时确定             |
| 灵活性       | 适应任意大小的数据集             | 只能处理预定最大规模             |
| 内存利用率   | 高（按需申请）                   | 低（预留过大则浪费，过小则不够） |
| 适用场景     | 数据量不确定的外部输入           | 已知固定大小的数据               |

### 本项目的具体理由

1. **数据量不确定**：数据集有23,203条记录，且程序需要"支持任意大小文件"。静态数组无法在编译时确定这一规模。
2. **内存效率**：初始分配1000条（`INITIAL_CAPACITY`），满时翻倍扩容（1000→2000→4000→8000→16000→32000），23,203条数据经历5次扩容，最终占用32000条空间。相比直接分配 `WaterRecord[30000]`，动态方案在不确切知道数据量时逐步扩展，内存峰值可控。
3. **程序鲁棒性**：若CSV文件只有几百条数据，动态数组不会浪费数十万字节的内存；若有数十万条数据，动态扩容也能应对（只要系统内存允许），静态数组则会溢出或编译失败。
4. **C语言标准实践**：处理外部输入文件时，动态内存是标准做法（`fgets` + `realloc` 模式）。

### 结构体设计说明

```c
typedef struct {
    char timestamp[32];    // 时间戳字符串 "2025-01-01 12:00"
    double temp;           // 水温 (℃)
    double salinity;       // 盐度 (PSU)
    double pH;             // pH值
    double DO;             // 溶解氧 (mg/L)
    double precipitation;  // 降水量 (m)
    double air_temp;       // 气温 (℃)
    bool valid;            // 数据有效性标记
} WaterRecord;

typedef struct {
    WaterRecord *records;  // 动态数组指针
    size_t total_count;    // 总记录数
    size_t valid_count;    // 有效记录数
    size_t capacity;       // 当前容量
    bool preprocessed;      // 是否已执行预处理（异常值+缺失值+滤波）
} WaterDataset;
```

`valid` 字段用于标记该记录的数值字段是否包含缺失值（空值、NaN、-999等），允许保留原始记录位置的同时标记数据质量问题，便于后续预处理模块处理。

`preprocessed` 字段用于追踪数据清洗状态：加载时初始化为 `false`，预处理完成后置 `true`，数据修改/删除后重置为 `false`。分析模块以此判断是否需要提醒用户先执行预处理。

## 1.2 CSV 列数兼容设计

### 问题背景

原始 CSV 数据为 **6 列**（无时间戳列）：Temp, Salinity, pH, DO, precipitation, Air_temp。但系统设计时预留了 **7 列**（含时间戳列）的兼容能力，以便支持带时间戳的外部数据。

### 兼容策略

`load_csv_data` 通过 `field_count` 和 `offset` 变量实现灵活适配：

| CSV 格式 | `field_count` | `offset` | 时间戳来源 |
|----------|:---:|:---:|------|
| 6 列（原始数据） | ≥ 6 | 0 | 自动生成（从 2025-01-01 12:00 起，每 5 分钟递增） |
| 7 列（带时间戳） | ≥ 7 | 1 | 从第 0 列读取 |

### 时间戳自动生成算法

6 列 CSV 没有时间戳列，需按任务书要求自动生成。**初版实现存在两个关键 BUG**，最终版本如下：

```c
// 正确实现：使用 mktime() + strftime() 标准日历函数
int total_minutes = (int)dataset->total_count * 5;  // 每条记录 +5 分钟
struct tm base = {0};
base.tm_year = 2025 - 1900;  // 2025 年（任务书 §3.2 明确要求）
base.tm_mon  = 0;            // 1 月
base.tm_mday = 1;
base.tm_hour = 12;           // 12:00 起始
base.tm_min  = 0;
base.tm_sec  = 0;
time_t t = mktime(&base) + total_minutes * 60;
struct tm *local = localtime(&t);
strftime(rec->timestamp, sizeof(rec->timestamp), "%Y-%m-%d %H:%M:%S", local);
```

**为什么必须用 `mktime` 而非直接拼日期字符串？**

| 方式 | 问题 | 示例 |
|------|------|------|
| ❌ `sprintf("2024-01-%02d", day)` | 日索引 > 31 时产生非法日期 | `2024-01-81` |
| ✅ `mktime + strftime` | 自动进位（月/年/闰年） | 第 31 天 → 第 32 天自动转为 2 月 1 日 |

`mktime` 负责标准化日历运算：传入的 `tm_mday=32` 会被自动规整为次月 1 日，`tm_mon=12` 会被自动规整为次年 1 月。这是 C 标准库确保日期合法性的正确做法。

## 1.3 存储格式讨论 — CSV vs 二进制

### 对比分析

| 维度       | CSV文本格式         | 二进制格式         |
| ---------- | ------------------- | ------------------ |
| 可读       | ✅ 是               | ❌ 否              |
| 文件体积   | 大（文本表示）      | 小（原始字节）     |
| 读写速度   | 慢（需解析/格式化） | 快（直接内存映射） |
| 跨平台兼容 | ✅ 通用             | ⚠️ 需考虑字节序  |
| 编辑便利   | ✅ 任何文本编辑器   | ❌ 需专用工具      |
| 顺序读取   | ✅                  | ✅                 |
| 随机读取   | ⚠️ 需逐行扫描     | ✅ 可直接seek      |

### 适用场景

- **CSV格式适合**：数据交换（与其他系统/人员共享）、人工审核编辑、跨平台数据迁移、需要人审查的中间结果。
- **二进制格式适合**：程序内部频繁读写、大数据集的快速存取、对存储空间有严格限制的场景、不需要人直接查看的中间缓存。

### 实际存储大小与理论值的差异原因

理论原始数据大小 = `sizeof(WaterRecord) × 记录数`。但实际文件大小可能不同：

1. **CSV比理论大**：数值被展开为可读文本（如 `25.60` 占5字节而非8字节的double），加上逗号、换行符、表头行，实际大小显著增加。
2. **文件系统簇大小**：磁盘以簇（通常4KB）为单位分配，小文件也会占用整数倍簇大小。
3. **编码开销**：CSV以ASCII/UTF-8存储，二进制约等于内存结构大小加少量元信息。

## 1.4 数据查询设计

- **分页浏览**：每页15条（`PAGE_SIZE=15`），支持 N(下一页)/P(上一页)/J(跳转到指定页)/Q(返回)。
- **按条件筛选**：用户输入参数名+范围（min/max），遍历所有有效记录并输出匹配项，最多显示前100条。
- **按参数排序**：使用 `qsort` 对任意数值字段进行升序/降序排列，显示前50条。排序在副本上进行，不改变原始数据顺序。

## 1.5 数据修改

- 通过记录号定位目标记录
- 修改前显示该记录的当前全部字段值
- 新值必须在任务书规定的合理范围内，否则拒绝修改
- 修改前自动调用 `backup_dataset()` 备份原始数据
- 修改后询问用户是否保存到文件

## 1.6 数据删除

- **单条删除**：输入记录号 → 确认 → 备份 → 删除（前移后续记录）
- **批量删除**：输入参数名+范围 → 统计匹配数 → 确认 → 备份 → 批量删除
- 删除后自动更新 `valid_count` 并刷新数据概览文件

## 1.7 备份与恢复

- **备份**：生成带时间戳的文件名（`backup_YYYYMMDD_HHMMSS.csv`），存储于 `backup/` 目录
- **恢复**：列出所有可用备份 → 用户选择 → 验证格式（列数=6或7，字段数正确） → 加载到内存

## BUG 修复记录

> 以下 BUG 在模块三集成测试阶段发现，根因均在模块一的 `data_io.c`。

### BUG-1：CSV 列数不匹配 — 所有数据显示 0.0 🔴

| 项目 | 说明 |
|------|------|
| **发现时间** | 模块三集成测试（2026-06-15） |
| **现象** | 数据浏览和所有分析结果均为 0.0，统计报告全为空 |
| **根因** | 实际 CSV 为 **6 列**（无时间戳列），但 `load_csv_data` 的解析条件为 `field_count < 7`，**全部 23,203 条记录被判定为格式错误**，标记为 `valid=false` |
| **影响范围** | 所有依赖数据的操作（浏览、筛选、分析、统计） |
| **修复方案** | ① `field_count < 7` → `< 6`；② 新增 `offset` 变量（6 列时 =0，7 列时 =1），统一数值字段索引；③ 6 列时自动生成时间戳 |
| **修复位置** | `src/data_io.c` 第 191-216 行 |
| **教训** | 硬编码列数是脆弱的——应用灵活适配，以实际数据格式为准 |

### BUG-2：时间戳自动生成溢出 — 非法日期 🟡

| 项目 | 说明 |
|------|------|
| **发现时间** | 模块三分析输出（同日） |
| **现象** | 后期记录时间戳出现 `2024-01-81`、`2024-01-99`、`2024-01-155` 等非法日期；盐度和缺氧预警按天分组结果混乱 |
| **根因** | 初版时间戳使用 `sprintf(ts, "2024-01-%02d 12:%02d:%02d", day_index, ...)` 硬编码拼凑日期。当记录数 > 31×288 时，`day_index` 超过 31，`%02d` 直接输出 `81`、`99` 等值，不会自动进位到 2 月 |
| **影响范围** | 所有时序分析（分段统计、预警）——日期错误导致按天分组失败 |
| **修复方案** | ① 改用 `mktime()` + `localtime()` + `strftime()` 标准日历函数——`mktime` 自动处理月/年进位和闰年；② 时间基准从 2024-01-01 修正为任务书要求的 **2025-01-01 12:00** |
| **修复位置** | `src/data_io.c` 第 203-216 行 |
| **教训** | 日期运算必须使用标准库函数——手动拼凑字符串永远无法正确处理日历边界（大小月、闰年、跨年） |
